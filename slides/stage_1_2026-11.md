# Intl Supported Time Zone Options
## For Stage 1
### Shane F Carr — November 2026 TC39

---

## Background: Time Zone Enumeration

ECMA-402 provides two APIs for enumerating primary time zones:
- `Intl.supportedValuesOf("timeZone")` — UI time zone pickers
- `Intl.Locale.prototype.getTimeZones()` — per-region time zones

Primary zones in TZDB & CLDR (`timezone.xml`) fall into two groups:
- **Location-based** (country/region): `"America/New_York"`, `"Asia/Tokyo"`, …
- **Non-location** (`"001"`): `"UTC"`, `"Etc/GMT±N"`, `"EST5EDT"`, …

---

## Problem 1: Cross-Browser Divergence (#778, #1052)

Engines diverge on non-location zones in `supportedValuesOf`:

| Category | Examples | Chrome | Safari < 26 | Safari 26+ | Firefox |
| :--- | :--- | :---: | :---: | :---: | :---: |
| Location-based | `"America/New_York"` | Included | Included | Included | Included |
| UTC | `"UTC"` | Omitted | Included | Included | Included |
| Fixed-offset `Etc/GMT*` | `"Etc/GMT+5"` | Omitted | Omitted | Included | Included |
| Legacy POSIX | `"EST5EDT"` | Omitted | Omitted | Omitted | Omitted* |

*\*Firefox patched `supportedValuesOf` to omit legacy POSIX zones.*

`Locale("en-001").getTimeZones()` returns `Etc/*` vs. `[]` in Firefox.

---

## Problem 2: TZDB 2026d Legacy POSIX Zones (#1103)

- **TZDB 2024b:** Linked POSIX zones to cities (`EST5EDT` → `America/New_York`, `PST8PDT` → `America/Los_Angeles`, …).
- **TZDB 2026d & CLDR 48:** Restored them as primary `Zone`s on perpetual US DST.
- **Impact on Web Users:**
  - Current spec includes them in `supportedValuesOf("timeZone")`.
  - Labeled like cities (`"Pacific Time"`), so `"EST"` / `"PST"` searches pick them and break if DST changes.
  - Re-aliasing to cities breaks once no city observes those rules.

---

## Stage 1 Problem Statement

Agreed by ECMA-402 / TG2 ([Issue #3](https://github.com/tc39/proposal-intl-supported-time-zone-options/issues/3)):

> Engines diverge in the set of zones that are returned from `Intl.supportedValuesOf`. We want to align engines on a default behavior, while also researching use cases to tailor the set in various ways.

---

## Proposed Default Behavior

<div class="columns">
<div>

Return **location-based zones + `"UTC"`**:
- Includes `"UTC"` (servers & logs; [#2](https://github.com/tc39/proposal-intl-supported-time-zone-options/issues/2))
- Excludes `"Etc/GMT±N"` (`Etc/GMT+5` is UTC−5; full-hour only)
- Excludes `"EST5EDT"` etc.
- `Locale("en-001")` → `["UTC"]`

</div>
<div>

```javascript
const zones =
  Intl.supportedValuesOf("timeZone");

zones.includes("America/New_York"); // true
zones.includes("UTC");              // true

zones.includes("Etc/GMT+5");        // false
zones.includes("EST5EDT");          // false

// Still valid in Temporal & DateTimeFormat!
Temporal.ZonedDateTime.from(
  "2026-11-30T10:00[Etc/GMT+5]"
);
```

</div>
</div>

## Stage 1 Exploration: Tailoring the Returned Set

<div class="columns">
<div>

**Strawman in Explainer:**
```javascript
Intl.supportedValuesOf("timeZone", {
  // "utc" (default)
  // | "none"
  // | "offset"
  // | "all"
  includeNonLocation: "offset",
});
```

</div>
<div>

**Questions for Stage 1:**
- **Need for options:** Non-picker use cases vs. default only?
- **Safe naming:** `"all"` misleads picker authors — name legacy opt-in explicitly.
- **Aliases ([#1](https://github.com/tc39/proposal-intl-supported-time-zone-options/issues/1)):** Non-primary `Link`s (`"US/Eastern"`)?
